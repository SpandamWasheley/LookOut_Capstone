# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview

**LookOut** is a barangay (Philippine village) security system with three independent apps that talk to each other only over the REST API — there is no shared code or types between them:

- **`lookout_backend/`** — Django REST Framework API + AI detection pipelines (single Django app: `core`). SQLite database.
- **`lookout/`** — Vite + React 19 web dashboard for admins and dispatchers.
- **`officer_app/`** — Expo (React Native) mobile app for officers, using Expo Router.

All three read/write the same backend at `http://localhost:8000/api` (or a LAN IP for the mobile app — see below).

## Scope (read first)

- **LookOut is a SINGLE-camera system** (one Hikvision DS-2CD1047G2, `Camera` code `CAM-SMOKE-01`, shown as "Hikvision DS-2CD1047G2"). Never add UI, seed data or defaults that imply multiple cameras. All `watch_*` commands default to `--camera CAM-SMOKE-01`.
- **Violation types in scope: parking obstruction, smoking, holdup (theft), drinking, improper disposal — nothing else.** Curfew and noise are permanently out of scope: do not re-add them to the UI, commands or docs. The `curfew_*`/`noise_*`/`waste_*`/`guardian_check`/`unknown_alert`/`email_alerts`/`auto_dispatch` settings columns, the `/sms/send/` endpoint and the household/resident models have been removed; do not re-add them. **SMS is the one exception to "out of scope", and it now SENDS.** `User.phone`, `User.sms_alerts` and the `SystemSettings.sms_alerts_enabled` master switch (migrations 0071/0072) are stored and editable, and `core/sms.py` delivers through **UniSMS** (`unismsapi.com`) on TWO triggers, split by urgency: a **holdup or parking obstruction** texts its assigned officer the instant it is assigned, and everything else is counted into a **half-hourly digest** (`manage.py sms_digest`) that also tells admins and dispatchers how many violations were detected. `/sms/send/` stays removed — there is no ad-hoc "text these people" endpoint and no bulk route; nobody passes in a recipient list. Push (`core/push.py`) is still the primary channel and the one always attempted. Do not confuse the provider with the unrelated Chinese service of the same name (`unisms.apistd.com`, `accessKeyId` + per-message `signature`) — wrong API entirely.
- **Improper disposal** (`disposal`, green `#22c55e`) was added after the original four and supersedes the old blanket "waste is out of scope" rule — but only under its own name and its own columns (`disposal_enabled`/`disposal_confidence`/`disposal_static_seconds`/`disposal_cooldown`). It does **not** revive the removed `waste_*` columns. It is the one detector that runs no trained violation class: `core/vision/disposal.py` finds objects that appear and then STOP MOVING (dual MOG2 background subtraction), then confirms them as a garbage bag with a zero-shot YOLO-World check prompted against both wanted and look-alike classes. It **is** a scored detector: `scoring.DISPOSAL_WEIGHTS` (object 0.40 GATE, arrival 0.20, person 0.10, left 0.25, persisted 0.05 — total 1.00), with `object` in `GATE_CUES` and `left` conditional on `person`. **Those weights are OURS, not cited** — unlike the other three tables, which come from published studies. The cue STRUCTURE is the standard abandoned-object formulation (a person brought it, it went static, they left it) that PETS2006 / AVSS-i-LIDS are built around; the numbers are tuned on this barangay's footage and must be described that way, never as measurements. Disposal carried no table at all until the boolean version of this same evidence proved worse: used as GATES, a missed person detection — routine at distance or at night — withheld a real violation entirely instead of weakening its case. `confidence`/`object_confidence` are still the zero-shot bag score, and `cues` now carries the full vector, so the alert card renders disposal's breakdown through the same checklist path as the other four. `disposal_confidence` is the GATE's floor: a bag check that leads every look-alike and clears it fires `object`, and with no gate cue there is no event and nothing is written (the spec's first rule, same as every other detector). The 0.55 / 0.75 thresholds then decide Monitoring / Possible / Likely, so a confirmed bag with nothing else known is 0.40 — the watchlist — rather than an instant alert. **`arrival`** is measured against a reference frame kept from a few seconds before the blob was born: the object's patch must have changed more than the ground around it (the ring guard is what rejects a headlight wash), re-asked every 0.25s with a consecutive-pass counter and no latch, so a transient cannot bank a pass. An unanswerable arrival — no reference frame yet — scores nothing rather than reading as a failure. **`person`/`left`** come from `claim_owners`, which reads the last `OWNER_LOOKBACK` seconds of person detections, not just the current frame, because the carrier is usually already walking away by the time their load shows up as static foreground. While the owner is still beside it the status is **capped** at Monitoring (`Score(cap=…)`, the mechanism smoking's puff gate uses) — not abandoned yet — while the score keeps accruing underneath. `watch_disposal`'s loop never names a level; a test enforces that. There is **one row per PLACE**: `SpatialCooldown` is a place→alert registry, so a candidate stage 1 raised fresh for a bag it had forgotten adopts the open row (status updates in place — `level` rises, `peak_level` never falls) instead of filing again, while rubbish further than `disposal_cooldown_dist` away is a separate violation. `disposal_cooldown` is an idle window on a place, re-armed every frame a live candidate owns a row. It shares no model forward pass with the merged detectors, so it is deliberately **not** part of `watch_all`/`watch_merged`/`watch_merged_all`; `core/monitor.py` launches it as its own live process, gated on `disposal_enabled` at launch time.
- **Facial recognition has been removed from LookOut and must not be re-added** — no face detection/matching, embeddings, enrollment, resident-matching or "matched person"/unknown-person features, in any layer (backend, web dashboard, officer app). Detection is object/behaviour-based only.
- **`Camera.edges` holds TWO areas, told apart by each entry's `type` (`core/zones.py`): `"zone"` is parking's no-parking road, `"disposal"` is where improper disposal watches for rubbish.** They share one JSON object and one `edges_width`/`edges_height`, so every reader asks `zones.has_road` (a disposal entry is never a road — `monitor.has_road_edge` would otherwise launch parking with nothing to judge against) and every writer uses `zones.with_road` / `with_disposal` + `zones.rescaled` rather than assigning `camera.edges = ...` (that deletes the other area). Both are optional and editable in Live Feeds → Edge Zones (second tab for disposal) and in Run Detection via the one `EdgeCanvas` (`kind="zone"|"disposal"`; drag a point to move it, right-click to remove it). A trace only ever fills in an area nobody has saved: `watch_parking` traces and saves a road only when `zones.has_road` is false (never onto a `-TEST` camera), and `watch_disposal` traces its own padded area per run without saving it. Saving one area restarts only that detector (`CameraViewSet.update` compares each area to what was stored before). The old `Camera.disposal_edges*` columns were removed (migration 0075 copies any saved area into `edges` first); do not re-add a second storage field.
- **"-TEST" cameras** (`CAM-<TYPE>-TEST`) are created by the Run Detection upload path to tag alerts from uploaded footage (used for accuracy evaluation). They must keep that suffix; `CameraViewSet` and `dashboard_stats` hide them from every camera list, but their alerts remain visible and filterable.
- The Live Feeds layout defaults to 1×1 on every visit and is intentionally not persisted.

## Architecture

### Backend: one fat `core` app

Everything lives in `lookout_backend/core/`: `models.py`, `views.py` (function-based views + DRF `ModelViewSet`s, no separate service layer), `serializers.py`, `urls.py` (a `DefaultRouter` plus a handful of plain function-based routes for auth/settings/dashboard-stats), `permissions.py` (`IsAdmin`, `IsAdminOrReadOnly`), `throttling.py` (per-endpoint rate limits for login/OTP/password-reset).

Auth is JWT (`djangorestframework_simplejwt`) with a custom `role` field on `User`: `admin` / `dispatcher` / `officer` / `both`. The login serializer embeds `role` and `name` in the token and echoes the full user object in the login response. Login returns **both** an access token (30 min) and a refresh token (7 days); both clients redeem the refresh token against `/api/auth/refresh/` on a 401 and retry the request once, each behind a single-flight guard so the 4-second polling can't fire parallel refreshes. The `role`/`name` claims survive a refresh. **Officer-vs-web access is a client-side gate, not a server-side one**: `lookout/src/api.js` rejects `role === "officer"` after a successful login, and `officer_app/lib/api.ts` rejects everything except `officer`/`both` — the backend itself doesn't stop an officer JWT from hitting other endpoints.

Business-readable codes (`CAM-01`, `OFC-01`, `ALT-0001`) are auto-assigned in each model's `save()` via the shared `_next_code()` helper in `models.py` — never set manually.

`Alert` is the violation record. Lifecycle: `active` → `dispatched` → `resolved`, or `active`/`dispatched` → `acknowledged` (dismissed). `AlertViewSet.accept` (`POST /api/alerts/{id}/accept/`) is the one non-CRUD action: it does an atomic M2M `.add()` of the requesting officer plus a status bump, specifically to avoid two officers' concurrent accepts clobbering each other the way a client-computed PATCH of the whole `officers_assigned` list would.

There are no websockets anywhere in this system — the web dashboard (`admin_dashboard.jsx`'s `useLiveOverviewData`) and the officer app (`AssignmentContext.tsx`) both get "real-time" updates by polling `/alerts/`, `/cameras/`, `/officers/` every 4 seconds.

**Push notification is the one thing that is not polled, because polling cannot do it.** The officer app's 4-second timer only runs while the app is open in the foreground, so an officer with it backgrounded or killed learned about an assignment when they next opened it. `core/push.py` sends through **Expo's push service** (`https://exp.host/--/api/v2/push/send` — not FCM directly, because EAS already holds the FCM credentials and a second copy of them here would be the larger problem). `DevicePushToken` is one row per INSTALL, `unique` on the token and **upserted on the token, not the user** — the same handset signed into by a second officer must move, or both would be notified of each other's work. The only trigger is `AlertViewSet.perform_update`, and it notifies `newly_assigned` — officers added by *that* request — never everyone currently on the alert, or a dispatcher widening an assignment would re-ping whoever is already on their way. `accept` deliberately sends nothing: the officer assigning themselves is holding the phone. Sending is fire-and-forget on a thread (`notify_assignment_async`, which builds the messages on the request thread and closes its own connection), so a dispatcher's Assign can neither hang nor 500 on Expo being unreachable. Delivery stays **best-effort and never authoritative** — the poll remains the source of truth and a notification is only a nudge to go and look — which is why nothing is queued or retried, and why tokens are only deleted on Expo's own `DeviceNotRegistered`, never on a transient rejection. Three things gate it, and each is load-bearing: sending is allowed only when the CALLER is admin/dispatcher/both (`AlertViewSet` sets no `permission_classes`, so any signed-in account can PATCH `officers_assigned` — ungated, the notification would be a way to buzz every handset in the barangay on demand); registration is allowed only to `officer`/`both`, since it upserts on the token; and `messages_for` filters on `user__is_active`, because deactivating an account stops it signing in but does not delete its devices. `POST /api/auth/logout/` **deletes the account's device rows** — all of them, since nothing in that request says which handset — so a successful sign-out stops the phone even when the app has forgotten which token it registered. Do not remove that: the app re-registers on every launch, so a second device is quiet only until next opened, while a shared duty handset still announcing the previous officer's violations is the worse failure. `core/tests_push.py` covers it; `core.push.deliver` is the seam, so nothing in the suite touches the network.

**SMS is the second channel to a phone, through UniSMS (`core/sms.py`).** It exists alongside push rather than instead of it because the two fail independently: push needs the app installed, permission granted and a data connection, a text needs only signal.

**There are TWO triggers, and the split is by how long the violation can wait — not by how certain the detection is.** `sms.URGENT_TYPE_CODES` is `{"theft", "parking"}`: a holdup in progress or a vehicle blocking the road needs somebody walking towards it now, so those keep the original instant path. Smoking, drinking and improper disposal are still violations worth attending, but nothing changes in the thirty minutes it takes to batch them, and an instant text per violation is one billed message per violation. The filter lives in `messages_for`, so every caller inherits it — do not re-decide urgency in a view. **Push is deliberately NOT filtered this way** and still fires for every type on assignment: it is free and instant, so cost is the only reason the list exists.

*Instant, on assignment* — `AlertViewSet.perform_update`, on `newly_assigned`, exactly as push is, so both channels inherit the rules push already had: only officers added by *that* request are told, `accept` sends nothing (the officer is holding the phone), and the CALLER must be admin/dispatcher/both. That last gate matters more here than it did for push: `AlertViewSet` sets no `permission_classes`, so ungated it would be a way for any signed-in account to spend the barangay's SMS credits — and it guards the `AssignmentNotice` write below for the same reason, or any account could inflate somebody's digest.

*The half-hourly digest* — `sms.send_digest()`, driven by `manage.py sms_digest` (`--every 30` to loop, `--dry-run` to see it, one-shot otherwise for Task Scheduler / cron). It is the only sender here that no user pressed a button for. Admins and dispatchers get "N new violations detected"; officers get "N assigned to you"; a `both` account gets **one** message carrying both numbers, because two would bill twice to say what one line says. A recipient with nothing to report gets nothing — a digest that said "0" every half hour would bill 48 messages a day per account. It is still not a bulk route: no endpoint, no recipient list, and who gets a message is decided entirely by role plus the same two opt-in switches.

Two pieces of state make the digest possible, and neither is a queue. **`SystemSettings.sms_digest_sent_at`** is the watermark the detected count runs from, so a run that was skipped (the PC was off) reports what it missed instead of losing it; null means "one interval ago", because the first run after the switch is turned on must not text somebody a count of every violation in the database. **`AssignmentNotice`** is one row per officer per alert, written in `perform_update` for exactly the assignments no instant text covered, because `Alert.officers_assigned` is a plain M2M with **no timestamp** — there is otherwise no way to tell a new assignment from one made last week, and counting on the alert's own `timestamp` instead would never count an officer working through a backlog. `texted_at` is what stops a row being counted twice. The two are deliberately asymmetric on failure: the **watermark always advances** ("the last 30 min" has to mean that, and one that only advanced on success would grow until it texted somebody a count of several thousand), while **notices are marked only for a recipient whose own message was accepted** — which is why `send_digest` delivers one message per call rather than one batch. A detection count is situational awareness the dashboard shows properly anyway; an assignment nobody was told about is work that never got dispatched. The count excludes **monitoring** events (a quiet watchlist that by definition notifies nobody, split on `peak_level` with a `level` fallback exactly as `AlertViewSet.get_queryset` does) and **`-TEST` camera** alerts (uploaded-footage evaluation runs are not events in the barangay, and one run can file dozens in a minute).

Three further things must ALL be true before one message is sent, and every one of them is opt-in because each message is billed: `SystemSettings.sms_alerts_enabled` (system-wide, off by default), `User.sms_alerts` (the account's own consent, off by default) and a non-blank `User.phone`. All three are read in `messages_for`, on the request thread, so the decision can never be made against a settings row that changed while a background thread waited. Sending is fire-and-forget on a thread (`notify_assignment_async`, mirroring push) and `deliver` is documented never to raise — a dispatcher's Assign must not hang or 500 on the provider.

Delivery is **best-effort and never authoritative**, exactly as push is: the 4-second poll stays the source of truth, so nothing is queued and a 429 gets ONE bounded wait (the provider's own `x-retry-after-ms`, capped) rather than a retry queue — assigning two officers at once makes a 429 predictable, and a silently un-texted second officer is a real failure.

Two provider constraints are load-bearing and shape the code. The sender ID is `Unisoft`, the provider's **shared** default, because registering a barangay-branded one needs an SID token plus business documents and the provider does not allow capstone projects to register one at all. Unisoft reaches **Globe and DITO only** — Smart/TNT/Sun are refused before any credit is spent, so those officers are push-only — and **cannot send a message containing a link**, which is why `_body` has none. `_body` is also kept inside one 160-character GSM-7 segment and folds non-GSM characters to plain equivalents (then to `?`): a zone name is operator-entered free text, and ONE smart apostrophe re-encodes the message as UCS-2 at 70 characters a segment, invisibly doubling the cost of every text the system sends.

`/sms/send/` stays removed and must not come back: the two triggers are an assignment and the digest's own clock, and there is deliberately no endpoint that texts an arbitrary list. `manage.py test_sms <number>` is the wiring check (it bypasses the two database switches on purpose and prints their state). `core/tests_sms.py` covers it; `core.sms.deliver` is the seam, so nothing in the suite touches the network. The officer app's Profile copy now says texts arrive "when available, on Globe and DITO numbers" — accurate about sending without promising delivery it cannot guarantee.

### AI detection pipeline (`core/vision/` + management commands)

`core/vision/recognition.py` is deliberately pure CV plumbing with **no Django model access**, so it stays importable/testable on its own. Pipeline: YOLOv8 (`ultralytics`) detects people and the violation objects (one merged model, `MODEL_PATH`); YOLOv8-pose supplies the keypoints for the mouth anchor (`find_mouth_pose`) and the hand-to-mouth gesture. There is no face recognition.

- The four in-scope detectors are `manage.py watch_smoking`, `watch_drinking`, `watch_parking` and `watch_thief` (plus `watch_all`/`watch_merged` which run several). Each re-loads `SystemSettings` every few seconds and creates an `Alert` with evidence saved under `media/violations/`. Thresholds are edited in Settings (Parking, Smoking, Holdup, Drinking panels).

**Parking's no-parking polygon can be traced automatically** (`core/vision/zone_autodetect.py`, `manage.py trace_zone`, `POST /api/detection-jobs/trace-zone/`). It runs the existing vehicle detector over a sampled clip and hulls the GROUND POINTS (bottom-centre of the box — the same point `ObstructionZone` tests) of vehicles that were seen to **move**. Two filters: a track must be seen `MIN_TRACK_SAMPLES` times (kills single-frame false positives) and must have travelled `MOVED_MIN_WIDTHS` of its own box width (kills parked vehicles — the rule cannot tell a car parked on the road from one in a yard, and a convex hull is maximally sensitive to outliers). It lives on the **detection-job** route and reads a `staged_token`, not a fresh upload: it belongs to the Run Detection flow, where the operator is already drawing the area and the clip (routinely 200 MB) is already on the server. A `file` is still accepted for scripts/tests; only that scratch copy is deleted afterwards, never a staged clip. It is a **suggestion, never a commit**: nothing is saved, the points come back in the staged frame's own pixels, and `RunDetectionPage` seeds them into the ordinary `EdgeCanvas` for the operator to check before pressing Start. The module takes boxes in and gives points out — no Django, no torch, no weights — so the geometry is unit-tested on synthetic rectangles; `recognition.detect_vehicles` is injected by the caller.

**Uploading a clip for a run is chunked and resumable, and must stay that way** — the source footage is routinely 200 MB, and a single multipart POST of that size times out through a tunnel and loses every byte. `UploadSessionViewSet` (`/api/uploads/`) takes a declared filename+size, then the pieces (`UploadSession.CHUNK_BYTES`, 5 MiB) into `media/uploads/partial/<id>/`, and `complete/` stitches them into an ordinary `media/uploads/` clip returning the same `staged_token` payload as `DetectionJobViewSet.frame` — so nothing downstream knows how the bytes arrived. Which chunks landed is read off the part directory, never stored in a column, so a resume cannot trust a counter the disk disagrees with. The driver is `lookout/src/chunkedUpload.js` (3 in flight, per-chunk retry); re-declaring the same file (name|size|lastModified fingerprint) returns the unfinished session instead of a new one, which is what makes a dropped request — or a page refresh — resume rather than restart. Abandoned sessions are swept by `_purge_stale_uploads`.

### Web dashboard (`lookout/`)

`App.jsx` + react-router-dom only handle the outermost auth routing: `/`, `/forgot-password`, `/dashboard`. Once logged in, **all internal page navigation is client-state, not URL-based**: `admin_dashboard.jsx` holds `activePage` and switches between page components (`CameraGrid`, `AlertFeed`, `RecordsPage`, `ResidentLog`, `RunDetectionPage`, `OfficersPage`, `SystemConfig`) directly — there's no `/cameras`, `/alerts`, etc. route. Which pages are reachable per role is the `ROLE_PAGES` map at the top of `admin_dashboard.jsx`.

The access token is kept **only in a module-level JS variable** in `api.js`, never in storage — a directly-usable bearer token should not be where script can read it, and it never needs persisting since a fresh one is one refresh call away. The **refresh token is persisted, in `sessionStorage`** (`lookout.refresh`), which is what lets a reload keep the session: `App.jsx` calls `restoreSession()` on mount, which redeems the stored token and re-reads `/auth/me/` for the user record, and routing waits on a `booting` flag so a reload doesn't flash the login screen. The refresh token also buys mid-session survival — a 30-minute access token would otherwise eject a dispatcher twice a shift.

**`sessionStorage`, not `localStorage`, is the deliberate choice** — don't "upgrade" it. Both are readable by a stored-XSS payload; what differs is blast radius. sessionStorage is scoped to the one tab and dies with it, so a stolen token's life is the working session rather than the refresh token's full 7 days and nothing is left in a closed browser. `localStorage` would be shared across tabs and persist indefinitely. The trade-off this accepts: a *new tab* starts logged out, and closing the tab ends the session. The officer app persists both tokens in `expo-secure-store` instead, because an app being killed and reopened is normal phone behaviour, not a red flag.

**Refresh tokens are single-use, and both flags are load-bearing** — `ROTATE_REFRESH_TOKENS` + `BLACKLIST_AFTER_ROTATION` with `rest_framework_simplejwt.token_blacklist` installed. Every `/auth/refresh/` returns a *new* refresh token and blacklists the one presented, so a token copied out of `sessionStorage` stops working the moment the real client refreshes. Turning either flag off silently removes the only revocation this system has; `tests_token_revocation.py` guards against that. Both clients already re-store `data.refresh` when a refresh response carries one, which is why rotation needed no client change.

`POST /api/auth/logout/` blacklists the refresh token so signing out ends the session server-side. It is **`AllowAny` on purpose**: holding the refresh token is the authorization, destroying it is the only thing the endpoint can do, and requiring a live access token would refuse to revoke anything for exactly the idle sessions that most need it. Both clients call it and neither awaits it (local tokens are cleared first, so sign-out never blocks on the network).

`REFRESH_TOKEN_LIFETIME` is 12h, overridable via `REFRESH_TOKEN_HOURS`. With rotation this is an **idle** timeout, not a hard cap — each rotation issues a full-lifetime token, so a session in use rolls forward and only an untouched one lapses. Officers who open the mobile app once a day will fall outside a 12h window and re-login each shift; raise `REFRESH_TOKEN_HOURS` if that is the wrong trade.

Not done, and the remaining weakness: the refresh token is still script-readable (`sessionStorage`). The stronger fix is an `HttpOnly; Secure` cookie scoped to `Path=/api/auth/refresh/`, which is non-trivial here because the dashboard and API are on different origins — it needs `SameSite=None; Secure`, `CORS_ALLOW_CREDENTIALS`, CSRF protection on that endpoint, and verification that third-party-cookie blocking doesn't break login from Vercel.

### Officer app (`officer_app/`)

Expo Router file-based routing under `app/`: `login`, `forgot-password`, `change-password`, `(tabs)/` (`index`=assignments, `history`, `profile`), `assignment/[id]`. All auth-based redirect logic is centralized in one place — `NavigationGuard` inside `app/_layout.tsx` — which reacts to `AuthContext`'s `officer`/`mustChangePassword` state; individual screens don't guard themselves.

`AssignmentContext.tsx` wraps the same `/alerts/` polling pattern as the web dashboard but reshapes `ApiAlert` into a mobile-friendly `Assignment` shape (`mapAlert`) and derives `activeAssignments` (`active`/`dispatched`) vs `historyAssignments` (`acknowledged`/`resolved`) from one alert list — there's no separate history endpoint.

Tokens persist across app restarts via `expo-secure-store` (OS Keychain/Keystore) on native, falling back to `AsyncStorage` on web (SecureStore has no web implementation).

### Email integration

- Email (Brevo's HTTP API, via the `core.mail.BrevoAPIBackend` email backend — not SMTP, which
  managed hosts commonly block) is used only for one-time verification codes: officer/dispatcher registration email verification and forgot-password OTPs (`EmailVerificationCode` model, 10-minute expiry hardcoded as `CODE_EXPIRY_MINUTES` in `views.py`).
