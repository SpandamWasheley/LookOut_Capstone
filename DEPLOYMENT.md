# Deploying LookOut

How to put the backend, the web dashboard and the officer app online, and where
the detection has to run.

---

## The shape of it

LookOut does not deploy to one place, and that is not a shortcoming of the
design — it is what CCTV analytics always looks like.

| Part | Where it runs | Why |
|---|---|---|
| Backend API + database | Cloud (Render) | Must be reachable by phones on mobile data |
| Web dashboard | Static host (Vercel or Netlify) | Plain files, free to serve |
| Officer app | Phones, built by Expo EAS | Needs a public API to reach |
| **Detection watchers** | **A PC at the barangay** | **Must see the cameras** |

**The detectors cannot go in the cloud.** Two reasons, both hard:

1. They read RTSP streams from cameras on the barangay's own network. A server
   in a datacentre has no route to `192.168.x.x`.
2. Their libraries (torch, insightface, onnxruntime) total several gigabytes,
   far past what a free cloud tier will even build.

So one PC sits with the cameras, runs the watchers, and writes into the same
cloud database the API reads from.

```
   Cameras ──RTSP──> Barangay PC ──┐
                    (watch_*)      │
                                   ├──> Cloud database <──> API ──> Dashboard
   Evidence photos ──> S3 bucket <─┘                                └─> Officer app
```

**This is why the S3 bucket is required, not optional.** The watchers save a
photo of each violation. If they save it to their own hard drive, the cloud
server cannot read it and every alert in the dashboard shows a broken image.
Both sides must write to the same bucket.

## Step 1 — Object storage (do this first)

Anything S3-compatible works. Free options that need no credit card:

- **Cloudflare R2** — 10 GB free, no charge for downloads (recommended)
- **Supabase Storage** — 1 GB free
- **Backblaze B2** — 10 GB free

Create a bucket, make it publicly readable, and generate an access key. Keep
these five values:

```
AWS_STORAGE_BUCKET_NAME    your bucket name
AWS_ACCESS_KEY_ID
AWS_SECRET_ACCESS_KEY
AWS_S3_ENDPOINT_URL        e.g. https://<account>.r2.cloudflarestorage.com
AWS_S3_CUSTOM_DOMAIN       the bucket's public URL host
```

Leave `AWS_STORAGE_BUCKET_NAME` unset and Django simply uses a local folder,
which is right for development.

## Step 2 — Backend on Render

The repository already contains `render.yaml`, so Render can read the whole
setup itself.

1. Push this branch to GitHub.
2. Render → **New** → **Blueprint** → pick the repo. It creates the web service
   and a free PostgreSQL database, and wires `DATABASE_URL` automatically.
3. Fill in the variables Render marks as required:

```
ALLOWED_HOSTS          lookout-api.onrender.com
CORS_ALLOWED_ORIGINS   https://your-dashboard.vercel.app
CSRF_TRUSTED_ORIGINS   https://your-dashboard.vercel.app
```

plus the five storage values from Step 1, and your email/SMS credentials
(`EMAIL_HOST_USER`, `EMAIL_HOST_PASSWORD`, `DEFAULT_FROM_EMAIL`,
`SEMAPHORE_API_KEY`).

`SECRET_KEY` is generated by Render. `DEBUG` is already `False`.

Migrations and `collectstatic` run automatically on every deploy.

> **The free tier sleeps.** After 15 minutes idle the service stops, and the
> next request takes ~50 seconds to wake it. Fine for a demo, painful for a
> live barangay. $7/month removes it.

Then create your first admin. `migrate` creates tables, not rows, so a new
deployment has an empty `User` table and no way to log in. Two things rule out
the obvious `createsuperuser`: Render's Shell is a paid feature, and the command
never prompts for `role`, so the account it makes defaults to `role="officer"` -
which `lookout/src/api.js` rejects at login, locking the superuser out of the
dashboard it was made for.

So it runs from the build instead. Set these three, then deploy:

```
ADMIN_USERNAME   brgyadmin
ADMIN_PASSWORD   <a strong temporary password>
ADMIN_EMAIL      you@example.com
```

`bootstrap_admin` creates one account with `role="admin"` and
`must_change_password=True`, so the dashboard forces a real password at first
login. It is idempotent and skips itself when the variables are unset - once the
account exists and you have changed the password, clear all three from the
environment.

## Step 3 — Web dashboard

Vercel or Netlify, both free. Config files for each are already in `lookout/`.

- **Root directory:** `lookout`
- **Build command:** `npm run build`
- **Output directory:** `dist`
- **Environment variable:** `VITE_API_URL=https://lookout-api.onrender.com/api`

> `VITE_*` variables are baked in **at build time**, not read when the page
> loads. Changing the API URL means triggering a rebuild — restarting does
> nothing.

The SPA rewrite in `vercel.json` / `netlify.toml` matters. Internal navigation
is client-side, so `/dashboard` is not a real file. Without the rewrite, anyone
who reloads that page gets a 404 — and because the access token is deliberately
held in memory only, reloading is exactly what people do after logging in.

## Step 4 — Officer app

```
npm install -g eas-cli
eas login
cd officer_app
eas build:configure      # links the project, writes the EAS project id
eas build --profile preview --platform android
```

`preview` produces an installable **APK** for sideloading — right for a
barangay rollout. `production` produces an **AAB** for the Play Store.

The API URL is already set per profile in `eas.json`; update it there to match
your Render hostname before building.

The Android package id is `ph.gov.barangay.lookout.officer`. **Choose it now if
you want something else** — it can never be changed once published to the Play
Store.

## Step 5 — The detection PC

Any Windows or Linux machine on the same network as the cameras. A GPU helps but
is not required.

```
git clone <repo> && cd LookOut/lookout_backend
pip install -r requirements.txt -r requirements-detection.txt
```

Give it a `.env` pointing at the **cloud** database and the **same** bucket:

```
DATABASE_URL=postgresql://...        # from Render, the EXTERNAL URL
AWS_STORAGE_BUCKET_NAME=...
AWS_ACCESS_KEY_ID=...
AWS_SECRET_ACCESS_KEY=...
AWS_S3_ENDPOINT_URL=...
AWS_S3_CUSTOM_DOMAIN=...
DEBUG=False
SECRET_KEY=<any value; this machine serves no web traffic>
ALLOWED_HOSTS=localhost
```

Then run the watchers:

```
python manage.py watch_parking --edges edges.json
python manage.py watch_curfew
python manage.py watch_all
```

They write alerts into the cloud database and evidence into the bucket, so both
appear in the dashboard and on the officers' phones within the 4-second polling
interval.

Use Task Scheduler (Windows) or systemd (Linux) to start them on boot.

> Render's **external** database URL is the one to use here — the internal one
> only resolves inside Render's network.

## Environment variables

| Variable | Where | Notes |
|---|---|---|
| `SECRET_KEY` | API, detection PC | Deploy refuses to start with the dev fallback |
| `DEBUG` | all | `False` in production |
| `ALLOWED_HOSTS` | API | Deploy refuses to start if left as `*` |
| `DATABASE_URL` | API, detection PC | Unset = SQLite (development only) |
| `CORS_ALLOWED_ORIGINS` | API | Dashboard origin, or the browser blocks every call |
| `CSRF_TRUSTED_ORIGINS` | API | Needed for the Django admin |
| `AWS_*` | API, detection PC | Must match on both, or evidence images break |
| `VITE_API_URL` | dashboard | Build-time only |
| `EXPO_PUBLIC_API_URL` | officer app | Set per profile in `eas.json` |

The API refuses to start with `DEBUG=False` if `SECRET_KEY` is still the
development fallback or `ALLOWED_HOSTS` is `*`. Both are silent failures
otherwise — a public signing key, or a server that accepts any Host header — so
they fail loudly instead.

---

## When something breaks

**Dashboard loads, every request fails.** `CORS_ALLOWED_ORIGINS` does not
include the dashboard's exact origin. It must match scheme and host with no
trailing slash.

**Alerts appear but images are broken.** The watchers and the API are not
pointed at the same bucket, or the bucket is not publicly readable.

**404 after reload on `/dashboard`.** The SPA rewrite is missing or the host
ignored the config file.

**Officer app cannot log in.** `EXPO_PUBLIC_API_URL` still points at a LAN
address. It must be the public HTTPS URL, and rebuilt — not just restarted.

**First request each morning takes a minute.** Free-tier sleep. Expected.

**Deploy fails installing torch.** Something is installing
`requirements-detection.txt` on the cloud host. Only the detection PC does that.
